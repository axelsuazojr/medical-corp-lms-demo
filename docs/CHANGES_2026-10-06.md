# LMS MEDICAL CORP — cambios solicitados (2026-10-06)

## Alcance realizado

### Web pública
- Rediseño corporativo de inicio, catálogo y detalle público de cursos.
- Se conserva información institucional y de cursos sin exponer calificaciones, promedio, asistencia o avance individual.
- Inicio de sesión únicamente con correo y contraseña; se retiraron Google y Microsoft/Outlook del flujo demo.
- Integración de contenido público con Payload mediante `site-pages`, con bloques reutilizables y preview para SUPER_ADMIN.

### Panel de estudiante
- Tarjetas del inicio enlazan a cursos, tareas, calificaciones y asistencia.
- Los recursos dejan de ser una sección global y viven dentro de cada clase/semana.
- Espacio de apuntes por clase con persistencia local en el navegador.
- Recursos por semana con soporte visual para PDF, Word, Excel, PowerPoint y enlaces.
- Tareas con instrucciones, carga de archivo, vista previa y estados pendiente/enviada/calificada.
- Foros con instrucciones e historial de participaciones tras enviar la participación.
- Registro de asistencia al entrar al curso con fecha y hora; la demo evita duplicar el mismo curso en el mismo día.
- Perfil con selector/vista previa de foto y formulario de cambio de contraseña.

### Panel de profesor
- Panel independiente bajo `/teacher`.
- Inicio con cursos asignados, estudiantes, actividades y alertas de seguimiento.
- Gestión de curso por semanas: recursos, tareas y foros, con controles de agregar/editar.
- Lista de alumnos y módulo de calificación por semana con puntuación y retroalimentación.
- Calendario que representa inicio/cierre de tareas y foros.
- Bandeja de mensajes de estudiantes separada.
- Dashboard de avance general y métricas por estudiante.
- Perfil con foto y cambio de contraseña.

### Panel administrativo / Payload
- Línea gráfica MEDICAL CORP y logo personalizado en Payload Admin.
- Administración de usuarios con cualquier rol para SUPER_ADMIN/CO_ADMIN.
- Colección `site-pages` exclusiva de SUPER_ADMIN para administrar la página pública por componentes.
- Preview del contenido público administrado.
- Cursos, recursos, tareas, foros, entregas, calificaciones, asistencia y archivos quedan modelados en Payload.
- Foros incluyen fecha/hora de inicio y cierre.
- Entregas incluyen retroalimentación docente, profesor calificador y fecha de calificación.
- Asistencia registra fecha/hora y, cuando crea un estudiante, fuerza su identidad y el origen `MODULE_ACCESS`.
- Archivos admiten PDF, Office, imágenes, audio, video, texto, CSV y ZIP.
- Se endurecieron campos sensibles de usuario para impedir que un usuario común cambie su rol, estado o permisos.
- Entregas, posts de foro y mensajes fuerzan la identidad del usuario autenticado cuando corresponde.

## Arquitectura actual

El repositorio sigue siendo un monorepo:
- `apps/web`: experiencia pública, estudiante y profesor.
- `apps/admin-api`: Payload CMS, API y modelo de datos.

La web pública consulta contenido publicado de Payload a través de endpoints sanitizados. Si el API no está disponible, usa contenido demo como fallback.

## Importante: demo vs. persistencia real

El proyecto original utilizaba autenticación demo por variables de entorno y gran parte de la UI estaba alimentada por fixtures. Para mantenerlo ejecutable sin introducir una migración de autenticación incompleta:
- apuntes del alumno, cargas/vistas previas de tareas y varias acciones del profesor funcionan como interacción demo/local;
- el esquema de Payload ya contiene los campos necesarios para persistir esas operaciones;
- el siguiente paso para producción es sustituir los fixtures y estado local por llamadas autenticadas a Payload (o un BFF) y unificar la sesión web con Payload Auth.

No se debe considerar todavía una implementación de producción de autenticación/autorización end-to-end.
